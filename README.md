# conversion-drop-diagnosis-demo

[![check](https://github.com/sproshchaev/conversion-drop-diagnosis-demo/actions/workflows/check.yml/badge.svg)](https://github.com/sproshchaev/conversion-drop-diagnosis-demo/actions/workflows/check.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

Учебная задача к статье на Хабре
«[Конверсия упала на 14% за ночь. Найдите причину за 20 минут](https://habr.com/ru/companies/otus/articles/1088882/)».

Дашборд интернет-магазина показывает конверсию 3,18% вместо вчерашних 3,70%. В данных
спрятаны две причины сразу: сломанный учёт покупок в новой версии iOS-приложения и сдвиг
состава трафика после рекламной кампании. Скрипт проходит диагностику по шагам и показывает,
сколько процентных пунктов дала каждая причина.

## Быстрый старт

Нужен только `python3`, сторонние пакеты не используются.

```bash
git clone https://github.com/sproshchaev/conversion-drop-diagnosis-demo.git
cd conversion-drop-diagnosis-demo
./run.sh
```

`run.sh` пересобирает данные генератором, проверяет, что они совпадают с `data/` байт в байт,
печатает разбор и сверяет вывод с `expected.txt`. При расхождении код выхода 1.

## Данные

Два дня, вторник 2026-10-06 и среда 2026-10-07, три платформы (web, android, ios), новые
и вернувшиеся пользователи.

| Файл | Что внутри |
|---|---|
| `data/sessions.csv` | число сессий по дню, платформе и типу пользователя |
| `data/sessions_by_source.csv` | число сессий по дню, платформе и источнику трафика: на сайте по UTM, в приложениях по атрибуции установок |
| `data/billing_orders.csv` | оплаченные заказы из биллинга: время, платформа, версия приложения, тип пользователя |
| `data/purchase_events.csv` | события `purchase` в продуктовой аналитике |

В среду в 06:00 выходит iOS 5.2 с новым экраном оплаты, и часть покупок с него не доходит
до аналитики. Биллинг при этом видит каждый заказ. В тот же день кампания приводит много новых
пользователей, больше всего на сайт и в Android-приложение
(19 000 сессий с меткой `telegram`, разрез в `data/sessions_by_source.csv`).

## Результат

**Дашборд по событиям `purchase`.**

| Платформа | CR, вт | CR, ср | Изменение |
|---|---:|---:|---:|
| web | 3,30% | 3,09% | −6,4% |
| android | 3,50% | 3,23% | −7,8% |
| ios | 4,57% | 3,31% | −27,6% |
| итого | 3,70% | 3,18% | −14,0% |

**Шаг 1. Сверка событий с биллингом за среду.** У web и android разрыва нет. У ios за сутки
28,0% оплаченных заказов остались без события `purchase`: до 06:00 разрыв нулевой, с 06:00
он 30,4%, и весь приходится на версию 5.2. Запрос считает заказы и события через
`count(DISTINCT ...)` в явных границах дня, поэтому повторно отправленные события не
размножают строки после соединения и выводятся отдельной колонкой `duplicate_events`.

**Шаг 2. Конверсия по заказам из биллинга.** 3,70% → 3,49%, падение 5,7% вместо 14%.
Сессий стало больше на 18,2%, заказов на 11,5%. Доля новых пользователей выросла
с 34,5% до 43,8%. По событиям конверсия новых почти не изменилась (1,61% → 1,59%),
по биллингу выросла (1,61% → 1,68%): события искажены пропусками на iOS.
Из 20 000 дополнительных сессий 19 000 пришли из `telegram`: 11 000 на сайт,
7 000 в Android и 1 000 в iOS. Остальные источники вместе дали ещё 1 000.

**Шаг 3. Разложение.**

| Составляющая | Вклад |
|---|---:|
| сломанный учёт iOS 5.2 | −0,31 п.п. |
| сдвиг состава трафика | −0,31 п.п. |
| конверсия внутри сегментов | +0,10 п.п. |
| итого по дашборду | −0,52 п.п. |

По биллингу конверсия выросла во всех шести сегментах, а общая упала. Это парадокс Симпсона:
вес сегментов с низкой конверсией вырос сильнее, чем подросла конверсия в каждом из них.

Полный вывод лежит в `expected.txt`.

## Как считается разложение

Общая конверсия равна сумме конверсий сегментов, взвешенных долей сессий. Изменение
раскладывается на три части:

- эффект состава: `sum((w_wed - w_tue) * r_tue)`;
- эффект сегментов: `sum(w_tue * (r_wed - r_tue))`;
- перекрёстный член: остаток, здесь он равен нулю.

Сегмент — пара «платформа × тип пользователя», конверсия считается по заказам из биллинга.
Вклад сломанного учёта — разница между конверсией по событиям и по биллингу в среду.

## Границы применимости

- Цифры учебные и подобраны так, чтобы две причины дали примерно равный вклад.
- Разложение зависит от выбора сегментов. Если состав сдвинулся по признаку, которого нет
  в разрезе (канал, регион), сдвиг попадёт в «эффект сегментов».
- Тип пользователя в учебных данных записан прямо в заказ. В реальной системе его нужно
  получить через устойчивую связь заказа с пользователем или сессией, иначе пересчёт
  конверсии по биллингу внутри сегментов не обоснован.
- Источник `telegram` у сессий в приложениях предполагает настроенную атрибуцию установок
  (Universal Links, App Links или аналог): обычная UTM-ссылка через магазин приложений
  источник не сохраняет.
- Разрез по источникам показывает связь прироста с кампанией, а не причинный эффект:
  это диагностика структуры изменения, а не эксперимент.
- Число оплаченных заказов — не выручка: средний чек и возвраты проверяются отдельно.
- Биллинг честен про заказы, но не про сессии. Если сломан учёт сессий, знаменатель
  придётся сверять с другим источником.
- Запрос сверки в `diagnose.py` написан на диалекте SQLite. В статье тот же запрос
  для PostgreSQL: вместо `substr(paid_at, 1, 13)` там
  `date_trunc('hour', paid_at, 'Europe/Moscow')`,
  а границы суток заданы как `timestamptz` с часовым поясом бизнеса. В учебных данных
  время уже записано в этом поясе, поэтому границы заданы строками.

## Структура

```text
.
├── data/                   готовые CSV, читателю генератор не нужен
├── gen_data.py             генератор данных с фиксированным seed
├── diagnose.py             диагностика по шагам: таблицы, сверка, разложение
├── expected.txt            эталонный вывод
├── run.sh                  проверка данных и вывода против эталона
└── .github/workflows/      та же проверка на каждый push
```
